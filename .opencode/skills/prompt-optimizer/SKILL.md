# 提示词优化

目标不是把提示词写长，而是把**模糊期待**变成**可检验的规格**。

交付物永远是：一段用户可以直接复制去跑的提示词（放在代码块里），外加 3–5 行说明（为什么这样写、哪里需要替换）。不是「建议你补充角色和格式」这种半成品。

## 铁律

1. **先问再写**。缺关键信息就不出成品。默认至少问一轮，最多三轮，每轮 3–4 个问题。
2. **给选项，别问开放题**。把「你想要什么角色」变成 A/B/C 选项，用户点一下就行；开放题只留「自定义」。
3. **一次一批**。按「任务 → 受众 → 约束 → 格式 → 验收」推进，不要一口气抛十个问题。
4. **不编造事实**。用户没给的背景、数据、产品名，用 `{{占位符}}` 标出，交付时列成待填清单。
5. **交付即可用**。成品必须是完整结构，复制粘贴就能跑；不允许出现「此处根据情况补充」。
6. **能用短的不写长**。每句话都要对应一个可检验的要求，删掉所有无法执行的形容词（专业、详细、高质量）。

## 何时触发

- 让我优化/改写/评审一段提示词
- 帮我写提示词、系统提示词、Agent 指令、角色设定
- AI 输出不稳定、跑偏、格式不对、太啰嗦 / 太简短
- 要一个可复用的提示词模板（写作、代码、分析、客服、教学……）
- 把一段口语化需求变成结构化 prompt

不触发：

- 只是问「提示词是什么」「LLM 原理」这类概念问题
- 只是让我按现有提示词执行任务（那直接做，不要反过来教学）
- 调 API 参数（temperature、top_p）——只在用户问输出稳定性时顺带提一句

## 工作流

### 第 0 步：判断模式（心里判断，不必宣布）

| 模式 | 触发条件 | 做法 |
|---|---|---|
| **A 从零起草** | 只说了需求，没有现成 prompt | 走完整三轮提问 |
| **B 优化现有** | 贴了一段 prompt / 描述现有写法 | 先诊断，只补缺失项，提问缩到 1 轮 |
| **C 只要模板** | 「给我个写周报的提示词模板」 | 问 2 个关键项（受众、长度），直接给模板 + 变量表 |
| **D 快速模式** | 用户说「别问了，直接给」/ 明显赶时间 | 按最合理假设写，开头列 3 条假设，结尾给 2 个变体 |

### 第 1 步：诊断（模式 B / C 必做）

按六要素快速打勾，只输出一行结论，不要长篇分析：

```
角色 ✓ | 目标 ✓ | 背景 ✗ | 输入 ✓ | 约束 ✗ | 格式 ✗
→ 主要缺背景和输出格式，先补这两块。
```

### 第 2 步：引导提问

用 `question` 工具发结构化选项；没有该工具时退化为编号列表，让用户回「1A 2B」。

**第一轮：任务与角色（必问）**

1. 任务类型：写作 / 编程 / 分析 / 教学 / 客服 / 创意 / 其他
2. 角色：从 `references/role-library.md` 取该类型 3 个差异明显的候选 + 自定义
3. 使用者/受众：谁看结果，他关心什么
4. 交付物形态：一段文字 / 一份文档 / 代码 / 表格 / 结构化数据

提问示例（question 工具的参数结构）：

```json
{
  "questions": [
    {
      "header": "任务类型",
      "question": "这个提示词主要用来做什么？",
      "options": [
        { "label": "写文案/内容", "description": "公众号、营销、产品介绍、邮件" },
        { "label": "写代码/改代码", "description": "实现、重构、审查、写测试" },
        { "label": "分析数据/文档", "description": "总结、对比、找问题、出结论" },
        { "label": "知识讲解/教学", "description": "把复杂概念讲清楚" }
      ]
    },
    {
      "header": "角色",
      "question": "希望 AI 以什么身份来回答？",
      "options": [
        { "label": "A 资深从业者", "description": "十年经验、做过真实项目，关注落地与风险" },
        { "label": "B 挑剔的评审者", "description": "专门挑毛病，关注边界、漏洞、维护成本" },
        { "label": "C 面向新手的教练", "description": "拆步骤、给类比、不默认你懂行话" }
      ]
    }
  ]
}
```

**第二轮：约束与格式（必问）**

1. 输出格式：Markdown 小节 / 表格 / JSON / 纯文本 / 代码块 / 列表
2. 长度：一句话 / 100 字内 / 300 字 / 不限制
3. 语气：专业克制 / 口语亲切 / 简洁直接 / 有感染力
4. 禁止项：不要编造数据、不要用感叹号、不要改接口、不要输出解释……

**第三轮：验收与示例（可选，模式 A 且任务复杂时问）**

1. 什么样的结果算合格（成功标准）
2. 有没有正例 / 反例可以贴
3. 是否需要「先给提纲，确认后再展开」的两段式

**提问规则**

- 用户已经回答过的不要再问。
- 能从上下文推断的，直接写进假设，不要浪费一轮。
- 用户答「随便 / 你定」时，选最稳妥的默认值，并在交付时标注「这一项我替你定了 X，可改」。
- 每轮结束后用一句话复述关键选择，让用户能纠偏。

### 第 3 步：起草

按下面的模板填，内部完成，不要展示碎片化的中间稿。

```text
# 角色
你是 {{领域}} 的 {{具体身份}}，擅长 {{能力}}。你的判断标准是 {{关注点}}。

# 任务
请完成：{{一句话说清交付物}}。

# 背景
{{为什么做、给谁用、上下游、已知信息、当前痛点}}

# 输入
{{材料原文 / 文件 / 数据 / 用户请求}}

# 要求
1. {{必须做到}}
2. {{必须遵守的规则或标准}}
3. {{禁止做的事}}

# 输出格式
{{结构、长度、语言、是否用表格/JSON/代码块}}

# 示例（可选）
输入：{{...}}
期望输出：{{...}}

# 完成后自检
逐条核对以上要求，不满足就重写，不要输出未达标的结果。
```

### 第 4 步：自检（交付前必须过）

逐项确认，任何一项不过就回去改：

| # | 检查项 | 合格标准 |
|---|---|---|
| 1 | 目标可判定 | 能用一句话说清，且能判断是否达成 |
| 2 | 角色具体 | 有身份 + 专长 + 关注点，不是「资深专家」空壳 |
| 3 | 受众明确 | 写清谁用、他在意什么 |
| 4 | 约束成对 | 既有「要做」也有「不要做」 |
| 5 | 格式可执行 | 具体到能直接照做（列、表、JSON 字段） |
| 6 | 无空话 | 没有「专业、详细、高质量、深入」这类无法执行的词 |
| 7 | 可替换 | 业务相关内容都抽成 `{{占位符}}` 并列表说明 |

### 第 5 步：交付

固定三段，简洁：

1. **成品提示词**（代码块，可直接复制）
2. **待填变量**（表格：占位符 / 含义 / 示例值）
3. **使用说明**（1–3 条：怎么调、什么时候该改哪一句、效果不好的话先动哪里）

最后问一句：要不要保存成 `.md` 文件（给出建议文件名）。用户说要才写文件。

## 怎么给角色（最容易做砸的一步）

角色 = **身份 + 专长 + 关注点 + 表达风格**。四个里缺两个就会退化成装饰。

- 每类给 3 个**差异明显**的候选，不要给三个同义词。
- 每个候选必须写清「他会在意什么」，这是用户做选择的依据。
- 一定附「自定义」。
- 用户选完后，把角色**扩写成 1–2 句具体描述**，不要照抄选项标题。

反例：`你是一个专业的程序员。`
正例：`你是做过多年的资深后端工程师，维护过高并发支付系统；你优先考虑边界条件、失败重试和数据一致性，宁可指出风险也不假设输入是干净的。`

完整角色库见 `references/role-library.md`。

## 常用技巧

按需选用，不要无脑全上。详细写法见 `references/patterns.md`。

- **Few-shot**：一个正例 + 一个反例，胜过十句形容词。
- **先提纲后展开**：长文、复杂方案先用两段式，避免跑偏后重写。
- **输出契约**：要程序处理就用 JSON，并给出字段说明和一个样例。
- **不确定性兜底**：「信息不足时先列出你需要我补充的问题，不要编造」。
- **自检回环**：结尾要求模型对照要求逐条核对再输出。
- **负向约束**：明确禁止项，比正面要求更能收住跑偏。

## 反模式（见到就改）

| 反模式 | 为什么不行 | 改成 |
|---|---|---|
| 堆形容词 | 模型无法执行 | 换成可检验的标准 |
| 一次塞多个任务 | 每样都半吊子 | 拆成多轮或分节输出 |
| 只给目标不给标准 | 结果随机 | 补长度、格式、受众 |
| 隐含前提不说 | 模型不知道你的项目背景 | 写进「背景」 |
| 只贴材料说「按上面」 | 跨轮指代易丢 | 每轮带全或明确引用 |
| 用「请认真思考」代替结构 | 没有信息量 | 给步骤和检查项 |

## 边界情况

- **用户贴的 prompt 已经很完整**：跳过提问，只做诊断 + 微调，最多问 1 个确认问题，改完用 diff 形式说明动了哪几句。
- **写系统提示词 / Agent 指令**：额外补工具使用规则、失败兜底、输出 schema、禁止行为；提醒用户系统提示词要短、要可维护，把长知识放检索或文件里。
- **多语言**：问清输出语言；若原文是中文而目标是英文场景，角色和约束要按目标语文化，不要直译。
- **涉及代码**：默认加「不要改公共接口」「给完整文件或 unified diff」「说明改动理由」。
- **用户反复说「还是不对」**：不要继续加形容词，回头定位是哪一要素缺失，用「你现在最不满意哪一点：内容 / 语气 / 长度 / 格式」四选一重新收敛。

## 交付示例（压缩版）

用户：`帮我写个提示词，让 AI 帮我改周报。`

追问两轮后交付：

```text
你是带过 8 人团队的部门负责人，看周报只看三件事：本周产出、阻塞、下周计划。
请把下面的流水账改写成一份周报。

要求：
1. 按「本周完成 / 遇到的问题 / 下周计划」三段输出，每段不超过 4 条；
2. 每条以动词开头，带上可量化结果（没有就写「进行中」）；
3. 删除过程性描述和情绪表达，不新增原文没有的事实；
4. 语气客观简洁，不用感叹号和形容词。

输出：Markdown，300 字以内。

【原文】
{{粘贴你的流水账}}
```

待填变量：

| 占位符 | 含义 | 示例 |
|---|---|---|
| 原文 | 你的周报草稿 | 「这周改了登录页…」 |

使用说明：团队规模不同就改第一句的「8 人团队」；如果领导更关心风险，把「下周计划」换成「需要协调的资源」。
